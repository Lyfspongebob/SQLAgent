# 文档附件解析与按需上下文

## 1. 背景与目标

当前附件功能已支持图片和纯文本，但 PDF、Word、Excel 不能直接理解。把整份文件转换成文本后全部送入模型会带来三个问题：

- token 消耗不可控。
- 文档越长，模型越容易忽略真正相关的内容。
- SQL Agent 的多个候选请求会重复携带同一份大上下文，成本和延迟被放大。

本次目标不是“把所有内容一次性喂给模型”，而是建立两阶段附件处理：

1. 上传时解析文件，生成结构清单和可检索的解析产物。
2. 用户发送问题时，只读取与当前问题相关的页、章节或 Excel 数据区间。
3. 模型先获得文件格式、规模和目录信息，再获得必要的正文或表格片段。

## 2. 实施前状态

- `AttachmentKind` 只有 `IMAGE` 和 `TEXT`。
- 文本附件在上传时抽取并保存到 `extracted_text`。
- `AttachmentService.loadForMessage` 会加载附件原始字节。
- `DeepSeekService` 把文本附件整体追加到用户消息。
- 图片通过 `image_url` 数据地址发送。
- 没有文档清单、解析产物、按需读取或文档上下文预算。

## 3. 方案

### 3.1 文件类型

计划支持：

- PDF：`.pdf`
- Word：`.docx`、`.doc`
- Excel：`.xlsx`、`.xls`

继续支持现有图片和 UTF-8 文本文件。

### 3.2 上传阶段

```text
原始附件
  -> 扩展名 + 文件头校验
  -> 对应格式解析器
  -> DocumentArtifact
      - 文件级清单 manifest
      - 可定位内容单元 units
  -> 解析产物写入附件存储
  -> 清单元数据写入 chat_attachments
```

清单示例：

```text
PDF：12 页，10 页有文本，2 页疑似扫描件
Word：35 个段落，4 个表格，6 个标题
Excel：3 个工作表；成绩表 2431 行 × 18 列
```

### 3.3 发送阶段

```text
用户问题
  -> 读取文档清单
  -> 对文档单元做相关性选择
  -> 控制单文档和整条消息的字符预算
  -> 生成 document-context
  -> 与图片附件一起送入模型
```

文档正文不会再次以原始二进制发送。文档上下文作为受限文本附件发送，并带有来源定位：

```text
[数据库设计.pdf / 第 12 页]
[教学数据.xlsx / 成绩 / 行 1-31]
```

### 3.4 解析器

采用专用解析库，不使用正则猜测 Office 二进制格式：

- PDF：Apache PDFBox。
- Word/Excel：Apache POI。
- DOCX/XLSX 的结构化内容通过对应 OOXML 模型读取。
- DOC/XLS 通过 POI 的旧格式支持读取。

### 3.5 安全与资源限制

- 文件扩展名和文件头必须匹配。
- 文档大小、PDF 页数、段落数、工作表数和行数设上限。
- 解析设置字符预算，避免超大文档耗尽内存。
- 文档内容标记为不可信输入，模型不能执行其中的指令。
- 加密、损坏或不支持的文档返回明确错误。
- 解析失败时删除已经写入的原始对象，避免孤儿文件。

## 4. 数据模型

在 `chat_attachments` 中增加：

- `manifest_json`：紧凑的结构清单，供列表和上下文组装使用。
- `parsed_storage_key`：解析产物在附件存储中的键。
- `parser_version`：解析器版本，便于重建索引。

`AttachmentKind` 增加：

- `PDF`
- `WORD`
- `EXCEL`

`DocumentArtifact` 使用 JSON 保存，不把大段正文放入关系数据库。

## 6. 实际数据流

### 6.1 上传

```text
MultipartFile
  -> 文件头与扩展名校验
  -> 文档解析
  -> ParsedDocument
      manifest: DocumentManifest
      units: List<DocumentUnit>
  -> 原始文件写入 AttachmentStorage
  -> ParsedDocument JSON 写入 AttachmentStorage
  -> chat_attachments 保存 manifest_json /
     parsed_storage_key / parser_version
```

原始文件和解析产物使用不同的存储键，数据库只保存索引与紧凑清单。

### 6.2 发送消息

```text
用户问题
  -> 加载文档 ParsedDocument
  -> 清单始终进入上下文
  -> 按问题关键词、页码引用和 Sheet 名对 units 打分
  -> 每份文档最多选择配置数量的内容单元
  -> 控制单文档和整条消息字符预算
  -> 生成 document-context.txt
  -> 与图片附件一起进入 DeepSeek 请求
```

普通问题选择高相关片段；包含“总结、概括、全文、主要内容”等问题时，在预算内跨文档抽样，而不是只取开头。

### 6.3 文档单元

- PDF：页级单元，保留页码；同一页过长时按片段拆开。
- Word：按识别出的标题分组，段落和表格进入所属章节。
- Excel：按工作表和连续行块生成单元，保留 Sheet 名与行号。

模型只接收 locator、相关正文和选择依据，不接收原始 Office/PDF 二进制。

## 7. 验收标准

- PDF 可以生成页数、文本页数和目录清单。
- Word 可以生成段落、标题、表格和样例内容摘要。
- Excel 可以生成工作表、行列规模、表头和样例行。
- 用户询问某个页面、章节或工作表时，只选择相关单元，而不是整份文件。
- 文档上下文有明确字符上限。
- 图片仍通过现有多模态链路发送。
- 原有图片、文本附件测试继续通过。
- 新增 PDF、DOCX、XLSX 解析测试。
- 前端构建和后端完整测试通过。

## 9. 当前限制

- 扫描 PDF 首版只识别“疑似扫描页”，OCR 和页面视觉分析需要后续阶段。
- 复杂跨页表格、公式语义和图表不会被完整还原。
- 旧版 DOC/XLS 已接入 POI 读取逻辑，但没有生成旧格式测试夹具，需在真实文件上补验收。
- 首版采用服务端同步解析；生产环境应改为异步解析 Worker 和任务状态。
- 首版按需读取由后端相关性选择完成，后续再升级为模型可调用的文档读取工具。
- 目前采用关键词、页码和 Sheet 名匹配，不是语义向量检索。
- 大 Excel 只解析配置范围内的行；超出部分必须后续通过范围读取工具获取。
- DOCX/XLSX 宏文件不会执行宏，但旧格式和复杂嵌入对象仍需生产级隔离。

## 10. 验收结论

状态：已完成首版。

与最初方案相比，实际实现采用“服务端按问题选择内容单元”，尚未让模型主动发起 `read_document` 工具调用。这一取舍保证当前 DeepSeek 兼容接口即使不支持 function calling，也能实现清单先行、按需读取和 token 控制。后续可在不明显改动解析产物结构的前提下增加模型工具调用。
