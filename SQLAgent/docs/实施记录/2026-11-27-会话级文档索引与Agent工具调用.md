# 会话级文档索引与 Agent 工具调用

## 1. 背景

上一版附件已经支持 PDF、Word、Excel 解析，但还有三个结构性问题：

1. 文档只在当前消息中按需选择，不能贯穿整个会话。
2. SQL 生成、校验、执行仍是写死的候选投票和修复流水线。
3. 用户只能看到最终结果，看不到 Agent 执行了哪些步骤。

截图中的典型问题：

- 要求生成 INSERT 但不执行，固定流程在只读校验阶段丢弃全部候选。
- 询问表结构或字段详情，被强制进入 SQL 生成与执行。
- Word 文档同时包含 SELECT 和 INSERT，整个候选池因安全校验失败。
- 用户追问“这几个字段分别是什么”，缺少最小对话上下文。

## 2. 目标

- 上传附件在当前会话持续可检索。
- 文档使用持久化 chunk 索引，不依赖当前消息附件 ID。
- 模型自主选择工具，不再固定生成 5 个 SQL 后统一校验。
- SELECT 可以安全执行；INSERT/UPDATE/DELETE 可以生成和展示，但绝不执行。
- 工具调用过程以用户可理解的工作流显示，并持久化到消息历史。
- 保留原有 SQLAgentService2 作为兼容回退，但默认对话不再调用它。

## 3. 新会话文档架构

```text
上传附件
  -> 原始文件存储
  -> ParsedDocument JSON 存储
  -> document_chunks 持久化索引

发送消息
  -> 会话文档目录
  -> Agent 判断是否需要文档
  -> search_session_documents
  -> read_document_chunks
```

### 3.1 document_chunks

新增表保存：

- user_id
- session_id
- attachment_id
- locator
- type
- title
- content
- metadata_json
- char_count

PDF、Word、Excel 和 UTF-8 文本都会写入该索引。用户不再需要在后续消息重复上传同一文档。

### 3.2 旧附件兼容

旧附件没有 chunk 时，会话文档服务会读取已有的解析 JSON 并惰性建立索引，不需要重新上传。

### 3.3 会话边界

所有文档查询强制携带当前 user_id 和 session_id：

```text
search_session_documents
  -> 只搜索当前会话

read_document_chunks
  -> 只读取当前会话 chunk
```

会话删除时，原始文件、解析 JSON 和 document_chunks 一起删除。

## 4. Agent 运行时

默认聊天调用链：

```text
ChatService
  -> AgentRunner
      -> DeepSeek completeWithTools
      -> 解析 tool_calls
      -> AgentTool 执行
      -> 工具结果回填模型
      -> 继续或输出最终回答
```

限制：

- 默认最多 8 个模型决策轮次。
- 单次模型可并行请求多个工具。
- 每个工具都有 JSON Schema。
- 工具失败会作为观察结果返回模型，而不是直接终止整个回答。
- 最终回答仍必须经过模型，不允许后端拼装固定模板替代。

## 5. 工具列表

| 工具 | 用途 |
|---|---|
| list_session_documents | 列出当前会话文档 |
| get_session_document_manifest | 查看文件格式、页数、结构和限制 |
| search_session_documents | 检索相关页、章节或 Excel 行块 |
| read_document_chunks | 按 chunk、附件或 locator 读取完整片段 |
| inspect_database_schema | 读取真实表结构，可按表过滤 |
| validate_sql | 语法解析和只读分类，不执行 |
| execute_readonly_sql | 仅执行单条只读 SELECT |
| search_knowledge_base | 检索智谱应用知识库 |

工具是否启用：

- 会话文档工具始终启用。
- validate_sql 始终启用。
- 数据库结构和执行工具仅在当前消息有可用数据源时启用。
- 知识库工具仅在用户开启知识库时启用。

## 6. SQL 行为变化

### 6.1 生成 INSERT 但不执行

新流程：

```text
用户要求生成 INSERT
  -> Agent 判断是否需要 schema
  -> 可选调用 inspect_database_schema
  -> 直接生成 INSERT
  -> 不调用 execute_readonly_sql
  -> 返回 SQL，并说明未执行
```

即使模型额外调用 validate_sql，INSERT 也只会得到：

```text
read_only=false
executable=false
reason=包含非 SELECT 语句，可以生成和展示，但不能由只读执行工具运行
```

不会再因为候选 INSERT 被只读执行器拒绝而让整个回答消失。

### 6.2 询问表结构

```text
用户：users 表有几个字段？
  -> inspect_database_schema(table_name=users)
  -> 直接基于列信息回答
```

不会为了回答字段数量强制生成 SELECT COUNT 并执行。

用户继续问“这几个字段分别是什么”时，会提供最近 8 条消息的短上下文，模型可以继续检查 users 表。

### 6.3 Word 中同时包含 SELECT 和 INSERT

有数据源时：

```text
读取文档
  -> 拆出 SELECT 和 INSERT
  -> validate_sql(SELECT) -> execute_readonly_sql
  -> validate_sql(INSERT) -> 不执行
  -> 汇总两条语句的结果和风险
```

没有数据源时：

```text
读取文档
  -> 分别 validate_sql
  -> 告知 SELECT 安全、INSERT 不安全
  -> 明确说明没有数据源，因此无法实际执行 SELECT
```

数据库执行必须有数据源。单纯开启聊天页面不能连接用户数据库。

## 7. 前端工作流

新增 `POST /api/chat/send/stream` SSE 接口。

事件：

- `step`：单个步骤开始或完成。
- `result`：最终 ChatResponse。
- `error`：执行异常。

前端显示：

- 执行过程中自动展开工作流。
- 每一步显示标题、状态和简短工具结果。
- 最终回答中的工作流默认折叠，用户点击查看。
- 工作流 JSON 存入 chat_messages.agent_trace，历史会话重新打开后仍可查看。

不展示模型的隐藏思维过程，只展示：

- 模型请求了哪些工具。
- 工具读写了什么范围。
- 成功、失败和简短原因。
- 最终整理回答。

### 工作流保存异常修复

联调时出现“保存 Agent 工作流失败”。

根因：

- `RestTemplateConfig` 使用 `new ObjectMapper()` 覆盖了应用 JSON 配置。
- 该实例没有日期时间处理能力。
- Agent 步骤最初包含 `LocalDateTime`，序列化时抛出异常。

修复：

- 工作流时间字段改为 ISO 风格的字符串。
- 自定义 ObjectMapper 使用 Jackson builder 和上海时区配置。
- 工作流序列化失败时记录日志，但不再中断最终回答和消息保存。
- 新增 Agent 工作流 JSON 序列化测试。

### SSE 部署注意

Nginx 代理 `/api/chat/send/stream` 时需要：

```nginx
proxy_buffering off;
proxy_read_timeout 600s;
```

否则工作流事件可能被缓冲到请求结束才一起显示。

## 11. 已知限制

- 尚未执行真实 DeepSeek 在线工具调用验收，需要实际 API Key 验证模型工具兼容性。
- 会话文档目前是关键词和定位检索，不是向量语义检索。
- 旧图片可以记录在消息历史中，但跨消息按需视觉读取尚未实现；图片仍只在当前消息直接送入模型。
- 近期对话窗口固定为 8 条、每条 1000 字符，上下文管理仍是简化版本。
- 文档解析仍为同步；生产环境应改为异步索引任务。
- SQL 只读安全还依赖目标数据库使用只读账号作为最终防线。
- Nginx 部署 SSE 时需要关闭该接口的代理缓冲。
